Introduction

The mental model shift that separates power users from casual users — and the concrete practices that make it real

  • Who this is for: developers already using Claude Code who want to move from casual use to deliberate, high-leverage workflows
  • The gap: most people treat Claude Code like a smarter autocomplete — the power users treat it like a junior engineer with full project context
  • What changes: not the tools, but the mental model — context management, structured prompting, and composable workflows compound over time
  • What you'll leave with: a concrete set of practices you can apply in your next session — CLAUDE.md, verification loops, parallelism, hooks, and more
  • Format: 18 focused topics, each standalone — drop in anywhere, revisit what's relevant to your current project

The Core Constraint

The context window fills permanently with every exchange — every other technique in this workshop is a response to this single fact

  • Context fills fast: every message, file read, and command output stays in the conversation permanently
  • Quality degrades: performance drops noticeably past ~40% context usage — stay well under for critical work
  • "Context rot": stale, conflicting info from failed attempts actively poisons later responses
  • Fresh session wins: a new session with a sharp prompt almost always beats a long session patching mistakes
  • Shape context proactively: CLAUDE.md, .claudeignore, and Skills determine what loads before Claude even starts

CLAUDE.md: The Highest-Leverage Setup

A project-level file Claude reads automatically before every session — the most leveraged place to encode your codebase rules, commands, and constraints

  • Run /init to generate a starter, then prune it ruthlessly
  • Target under 200 lines — only what Claude genuinely can't infer from the code
  • Ask of each line: "Would removing this cause Claude to make mistakes?" If not, cut it
  • Layer it: project root + ~/.claude/CLAUDE.md (global) + subdirectory files via @path
  • Version-control it — the whole team can contribute and review changes
  • After every correction: "Update CLAUDE.md so you don't make that mistake again"
  • Rebuild every ~6 months — outdated constraints limit newer models

CLAUDE.md: What Goes In, What Stays Out

Build commands, architecture decisions, and non-obvious gotchas belong in — standard language patterns, full docs, and things the code already shows belong out

✅ Include

Build, test & lint commands
Project-specific scripts Claude can't guess: npm run dev, make test, ./gradlew build
Non-default code style
Linting rules, formatter config, naming conventions that differ from language standards
Architectural decisions
Why certain patterns are used, key constraints, branch naming, PR format
Common gotchas
Recurring mistakes, known workarounds, hidden constraints that aren't obvious from the code

❌ Exclude

Standard conventions
Language defaults Claude already knows — TypeScript patterns, Python idioms, React hooks
Full API docs
Link to documentation instead — never paste large reference blocks
Frequently changing things
Version numbers, team-specific ephemera, configs that shift often
What the code already shows
Patterns visible in the codebase — Claude can read the files directly

Verification Loops: The #1 Quality Tip

Asking Claude to verify its output against a concrete criterion — running tests, linting, checking a diff — catches errors before they compound into bigger ones

  • The problem: Claude stops when things "look done" — without a signal, you become the verification loop
  • Provide: tests, a build command, linter, diff script, or screenshot to compare against
  • Tell it explicitly: "Run the tests and fix until they all pass — don't stop before that"
  • Ask for evidence, not assertions: "Show me the test output" vs accepting "it's done"
  • Use Stop hooks to block completion until checks pass — hooks are enforced, instructions aren't
  • TDD workflow: write failing tests first → implement → Claude runs until green — eliminates whole classes of failure

The Power Workflow

A four-phase loop — explore the codebase, plan explicitly, implement incrementally, commit often — that consistently produces better results than diving straight into code

Explore

Have Claude read the relevant files first. Don't describe — let it see. @mention files to attach them directly, saving Read calls and improving accuracy.

Plan

Enter Plan mode (Shift+Tab) — Claude thinks without editing. Review the plan, edit it with Ctrl+G if needed, and approve before any code is written.

Implement

Exit plan mode and let Claude execute — with a verification loop built in. If things go sideways, return to plan mode and re-plan rather than pushing through.

Commit

Ask Claude to commit with a meaningful message and open a PR. Committing as you go creates restore points — cheap insurance for risky operations.

Prompting Like a Pro

Giving Claude explicit context, a clear scope, and a concrete output format removes guesswork and produces precise, useful results on the first try

  • @mention files, not descriptions — @auth.ts attaches the file and saves a Read call; describing paths makes Claude search and guess
  • Name existing patterns — "Follow the style of HotDogWidget.php" gives Claude a concrete target, not an abstraction
  • Scope tightly — include the file, the edge cases, the constraints, and what "done" looks like before Claude touches code
  • Paste screenshots — for UI work, a screenshot beats 300 words of description every time
  • Three-part bug reports — symptoms + likely location + what "fixed" looks like; three-part prompts get three-part fixes
  • Pipe data in — cat error.log | claude ... or allowlist URLs via /permissions — don't make Claude imagine the input

Advanced Prompt Patterns

Role-priming, constraint-setting, and structured output formats — techniques that reliably unlock deeper reasoning and more predictable responses

  • ultrathink — prefix complex tasks with "ultrathink this" to trigger deep reasoning before Claude writes a single line
  • Scrap and redo — "This approach isn't working. Scrap it and implement the elegant solution." resets bad momentum faster than patching
  • Prove it works — "Prove to me this works" forces Claude to run verification, not just assert success
  • Grill me on these changes — ask Claude to adversarially review its own output; it catches issues it glossed over the first time
  • TDD-first — "Write the failing tests first, then implement until green" eliminates whole classes of correctness failure
  • Re-plan on drift — when implementation wanders, Shift+Tab back to plan mode and re-plan rather than layering more prompts on a broken path

Parallelism

Splitting independent tasks across multiple Claude sessions and running them simultaneously — the fastest way to multiply your output without any extra cost

  • Run 3–5 sessions simultaneously — each working an independent task; your throughput multiplies while you review one session's output
  • Number your tabs — "Claude 1 is on auth, Claude 2 is on tests, Claude 3 is on the migration" — keeps your mental model clear under load
  • System notifications — enable them so sessions alert you when they need input; you stay unblocked without constant tab-switching
  • Web + CLI in parallel — claude.ai/code sessions and local CLI sessions can run concurrently and hand off work between them
  • Subagents for noisy work — exploratory searches, full test runs, codebase scans — offload to a subagent so your main context stays clean
  • Independent tasks only — parallelism breaks when sessions share files without coordination; keep work isolated or commit between handoffs

Git Worktrees

Multiple working directories checked out from the same repo simultaneously — each Claude session gets its own isolated branch so agents never step on each other

  • The problem with shared checkouts — two Claude sessions editing the same branch create merge conflicts and corrupt each other's context
  • Worktrees give each session its own branch — git worktree add ../feature-x feature-x spins up a clean copy in seconds
  • Native support — claude --worktree creates and enters a worktree automatically; no manual git plumbing required
  • Merge when done, not before — each session commits cleanly to its own branch; you review and merge after, not during
  • Disposable by design — git worktree remove cleans up; no lingering state to untangle if a task is abandoned
  • Combine with parallelism — worktree-per-session is the pattern that makes 3–5 concurrent sessions actually safe at scale

Hooks

Shell scripts that fire on specific Claude events — the only way to guarantee rules are always enforced, because hooks run unconditionally unlike instructions Claude can ignore

Hook Event Types

PreToolUse
Runs before any tool call — block writes to protected files, scrub credentials, validate format
PostToolUse
Runs after a tool completes — auto-format on write, run linter after edit, log changes
Stop
Runs when Claude finishes a turn — block completion until tests pass, enforce commit hygiene
Notification
Fires on system notifications — Slack alerts, desktop pings when a session needs input

Example: Stop Hook

{
  "hooks": {
    "Stop": [{
      "matcher": "",
      "hooks": [{
        "type": "command",
        "command": "npm test"
      }]
    }]
  }
}

Runs your test suite every time Claude finishes a turn. If tests fail, Claude is blocked from completing — no assertions of success without proof.

Token & Session Efficiency

Strategies to keep context lean — using .claudeignore, compacting summaries, and knowing when to start a fresh session rather than patching a degraded one

Session Commands

/clear
Start fresh between unrelated tasks — stale context is debt, not help
/compact
Compress before a break (cache expires ~5 min); use /rewind to undo without summarizing
Set model at start
Changing model or effort mid-conversation busts the prompt cache — pick once, stick with it
/context
Run in a fresh session to audit what's loaded; trim anything Claude doesn't actually need

.claudeignore

# Heavy dirs that slow reads
node_modules/
.git/
dist/
build/

# Generated files
*.lock
coverage/
*.min.js

# Secrets
.env*
*.pem

Works like .gitignore — Claude skips these entirely. Keeps context focused on your actual source.

Custom Skills & Slash Commands

Markdown files that become slash commands — package any repeatable workflow once and invoke it with a single command, loading nothing until it's actually needed

Slash Commands

Live in .claude/commands/
Any .md file becomes a /command — called with /command-name
Pass arguments
Use $ARGUMENTS in the file — "/review auth.ts" injects the filename automatically
Common uses
/security-review, /write-tests, /summarize-pr — any prompt you type more than twice
Team-shareable
Commit the commands/ dir — everyone on the team gets the same shortcuts instantly

Skills

Richer than commands
Structured instructions with tool guidance, MCP calls, and multi-step workflows
Zero cost when idle
Skills load only when invoked — no context overhead for instructions you're not using
Built-in examples
/sc:build, /sc:test, /sc:research — study these as templates for your own
Build your own
Save a .md in .claude/skills/ — any instructions you'd otherwise repeat every session

Subagents

Spawning a separate Claude session to handle a bounded task — keeping the main session clean while offloading work that would pollute it with irrelevant context

  • The problem they solve — exploratory work (codebase searches, full test runs, doc reads) floods your main context with noise before the real task even starts
  • Subagents get their own context — they run isolated, do the work, and return a clean summary; the main session never sees the mess
  • Spawn with the Agent tool — or via claude -p "..." for headless one-shot tasks from the CLI
  • Specialist roles — security-engineer, backend-architect, code-reviewer — route work to agents tuned for that domain
  • Parallel subagents — fan out multiple subagents simultaneously, collect results, synthesize in the main session
  • Cost awareness — each subagent is a full session; use them for genuinely expensive work, not trivial lookups you could @mention a file for

MEMORY.md & Auto-Memory

A structured memory file Claude reads and writes across sessions — storing user preferences, project decisions, and recurring context so nothing important has to be re-explained

  • What it is — a structured memory system Claude reads at the start of every session; unlike CLAUDE.md (project rules), memory stores evolving facts that update over time
  • Auto-Memory (2026) — Claude can now write and update its own memory automatically based on what it learns in your conversations
  • Scoped per project — memory lives in .claude/projects/.../memory/; individual topic files (e.g. user.md, feedback.md) and a MEMORY.md index
  • What to store — architectural decisions + rationale, team conventions that differ from defaults, recurring patterns, known codebase gotchas
  • What NOT to store — ephemeral state, task lists, anything already in code or CLAUDE.md — save the non-obvious stuff only
  • The payoff — cross-session continuity: Claude starts informed instead of blank, you stop re-explaining context every time

Power User Mindset

Treating Claude as a collaborator with full project context rather than a smart search box — the habits, mental models, and defaults that compound into dramatically better results over time

DO

Give Claude a full mental model upfront — codebase layout, constraints, goals
Use verification loops: "does this pass tests / render correctly / match the spec?"
Commit early and often — give Claude clean restore points to work from
Let Claude explore before it plans; let it plan before it codes
Delegate expensive research to subagents, keep main context clean
Treat Claude like a senior engineer: assign outcomes, not keystrokes

AVOID

Vague prompts with no context — "fix this" without specifying what fixed looks like
Trusting output without verifying — Claude is confident even when wrong
Working on main branch — always use a worktree or feature branch
Letting context rot — /clear or /compact before quality degrades
Overloading one session — split large tasks across focused sessions
Ignoring CLAUDE.md — it's the highest-leverage 30 minutes you'll ever spend
